# Stage 4.0 — RSM Substrate: Design Spec

**Date**: 2026-08-30
**Status**: Approved direction (this document). Implementation plan follows via writing-plans.
**Supersedes**: the "Key design decisions" sequencing assumption in ROADMAP.md § Stage 4 ("RSM may necessitate unforeseen changes to minkowski's internals" as the reason to order RSM before the query language).

---

## 1. Context

Stage 4 (Replicated State Machine) was to precede Stage 3.75 (semantic query language) because RSM might reshape internals the query language would hook into, forcing a rewrite of 3.75's execution surface.

An /adhd divergent pass (5 frames, 30 candidates, 3 deepened) against the actual codebase found the premise is mostly false — and narrowed what is true into four small, additive invariants. This spec records the reframe and the substrate that carries it.

### 1.1 The reframe

**RSM is external composition, not internals surgery.** The mutation-log, replay, and recovery seams RSM needs already exist in `minkowski-persist`:

| RSM requirement | Already shipped |
|---|---|
| Ordered mutation log | `EnumChangeSet` — deterministic, ordered, applies atomically |
| Wire format | `ReplicationBatch` (`to_bytes`/`from_bytes`, rkyv, transport-agnostic) |
| Follower apply | `apply_batch` — per-record apply with refusable id remap (`build_remap` pre-flights before any mutation). NOT atomic across records; failure semantics are specified in §2.7 |
| Log ↔ local-id translation | `build_remap` in WAL replay (TypeId/stable-name keyed, refusable) |
| State transfer | `recover_world` + `LsmRecovery` + manifest sequence bounds (Stage 3) |
| Durability tier | `Durable<S>` wrapping any `Transact` |

TigerBeetle's lesson is satisfied by construction: the consensus/replication **state machine** is separate from the **data structures**. `Replicated<S>` lands beside `Durable<S>` in `minkowski-persist`, not inside `World`.

### 1.2 What genuinely remains (the four invariants)

The deep-dive verified these are the only changes that reach minkowski core:

1. **INV-1 — Batch = tick.** A committed batch advances the world tick exactly once; `tick_after: u64` rides the batch header and replay set-and-verifies it.
2. **INV-2 — View fencing.** `view: u64` in the WAL frame header; stale-view frames die by generation mismatch, the same kill-path as stale `Entity` refs.
3. **INV-3 — Replica mode.** The one World-internal change: a read-only flag refusing `&mut` entry points when the world is a replica.
4. **INV-4 — `read_at(applied_seq)`.** One function is the entire integration point between RSM and any future read surface (including 3.75).

Everything else from the Stage 4 design (io_uring, zero-copy buffer identity, client session tables, reducer-intent replication, view-change orchestration) is deferred to Stages 4.1+ unchanged from the roadmap.

## 2. Design

### 2.1 Component layout (all external to World)

```
minkowski-persist
├── Durable<S>            (existing — WAL durability)
├── Replicated<S>         (new — wraps Durable<S>, Transact delegates)
│     ├── outbound pump: committed changesets → batch frames → peers
│     └── Views: ViewId minted only by install(quorum cert)
├── Follower              (new — owns applied_seq: AtomicU64)
│     ├── advance(batch) → apply_batch
│     └── read_at(seq, |world| ..) → gate then query_raw
└── WAL frame header      (additive: view field; batch header: tick_after)
```

### 2.2 INV-1 — Batch = tick

- `tick_after: u64` is attached to **each committed mutation record** (the per-commit unit), not to the `ReplicationBatch` transport envelope. A committed record advances the world tick exactly once; the tick becomes derivable from log position.
  - Granularity trap (codex review): `ReplicationBatch` is a transport envelope that can carry many committed records (`WalCursor::next_batch(limit)`); a batch-level tick would make `Changed<T>` semantics depend on the cursor's batch size. The tick moves with the commit, and replay set-and-verifies it per record.
- On replay, the world tick is set-and-verified against the record's `tick_after` — mismatch is a hard error (a replayed log that disagrees with its own tick watermark means corruption or a foreign log).
- Column `changed_tick`s rebuild correctly because `apply()` marks columns with the replayed record's tick.

**TigerBeetle lesson**: "the log is all the state" extended to state that today lives only in RAM.

### 2.3 INV-2 — View fencing as generational staleness

`ViewId` is a `Copy + Ord` newtype over u64, minted **only** by `Views::install(quorum certificate)` — the typed-construction-path discipline from the ID-principle table (forging prevented structurally; replicas can hold, copy, compare, stamp — never mint).

- Stamped into: WAL frame headers (beside CRC32 + seq), batch headers, IO completions, client acks.
- Runtime check: one compare at the receive/complete boundary — `hdr.view < views.current()` → drop. No ring quiesce; deposed leaders' in-flight writes die at the fence (roadmap: view changes do NOT drain I/O).
- Recovery backstop: replay validates each frame's view against the durable view history; frames from superseded or unknown views are discarded like orphan drains.

**Load-bearing constraint**: the durable view history must never be truncated and view fsync must precede the first prepare bearing that view — otherwise a restarted replica re-mints a historical view and the fence forges. This is a durability-ordering requirement, not a type-system one (entity generations never faced it because the allocator is in-process).

**Sub-decision (deferred to 4.1)**: bit-pack `ViewId` exactly like `Entity` (low bits = replica slot, high bits = view generation) and add a row to the ID-principle table: `ViewId | quorum certificate | u64`.

### 2.4 INV-3 — Replica mode

A `replica: bool` (or `WriteMode` enum) on World, checked at every `&mut self` mutation entry point (`spawn`, `insert`, `remove`, `despawn`, `apply`...). A replica world refuses direct mutation with a typed error; the ONLY mutation path is `Follower::advance` — and `apply_batch` internally must bypass the flag explicitly (documented internal seam), because follower apply is the exception that must go through.

**Why this is load-bearing**: convergence is only provable if every state change flows through the log. Today `&mut World` hands out mutation paths that bypass the WAL silently — a leader accumulates unreplicated state with no error. The flag converts that failure mode from "silent divergence" to "typed error at the call site".

**Bypass-path invariant** (per AGENTS.md): the `apply_batch`-bypasses-replica-flag seam must be documented as the deliberate exception, and the convergence test must prove that a replica world mutated through `advance` matches the leader bit-for-bit.

### 2.5 INV-4 — `read_at(applied_seq)`

```rust
impl Follower {
    pub fn read_at<R>(&self, seq: u64, f: impl FnOnce(&World) -> R) -> Result<R, Stale>
}
```

Checks `applied_seq >= seq`, then runs the closure (shared-ref, `query_raw`-based reads, no tick advancement). This is the ONLY surface the query language (3.75) is permitted to hook for replicated reads: 3.75 plans execute via `execute_*_raw` (already take `&World`, no tick advancement) inside `read_at` — the planner stays RSM-unaware and gains snapshot reads for free. If a 3.75 feature requires bypassing `read_at` to evaluate on replicated state, the feature is rejected or the surface must be expanded (same discipline as the 3.75 typestate invariant).

Staleness semantics: `read_at` provides **bounded-staleness reads** (consistent at a logged prefix), not linearizable reads — matching the roadmap. Linearizable reads route to the leader (4.1+, lease protocol).

### 2.6 The invisible state that is NOT in this substrate (explicit)

- **Entity generations / orphan drains**: NOT log-derivable today because orphan drains fire at arbitrary local times. 4.1 decides between (a) logging `GenerationBump(index)` records, and (b) drain pinning (moving drains to apply-time so generations become derivable). Option (b) is invasive but eliminates a record type. Until decided, a replica's post-apply generation state is defined by `apply_batch`'s explicit-id semantics; the convergence test pins the observable behavior.
- **Per-reader `Changed<T>` watermarks**: process-local by design. **Failover contract (documented, not fixed)**: the first `Changed<T>` query after failover may see everything (or nothing) as changed; readers re-read once. The tick is a lattice, not a scalar — per-query watermarks are unreplicable without read-lease machinery (4.1+).

### 2.7 Follower failure semantics (non-atomic apply is a fact, not a premise)

`apply_batch` applies records one by one with no rollback: a failure at record k leaves records 0..k applied. `AlreadyPlaced` is a refusable `ApplyError`, **not** an idempotent-success signal. The substrate therefore does not rely on atomicity or on treating replay errors as success:

- **Idempotency by position, not by error-tolerance**: the follower never re-applies an applied prefix. `applied_seq` is the dedup boundary — a batch whose records are all `<= applied_seq` is a no-op; re-apply idempotency is an invariant of the follower loop, not of `apply_batch`.
- **Pre-flight what can be pre-flighted**: id-remap validation already runs before any mutation (`build_remap` precedes the apply loop). Unremappable batches fail with zero mutation — the refusable-remap philosophy costs nothing here.
- **Mid-apply failure = poison-and-rejoin**: a failure inside the apply loop (e.g. `AlreadyPlaced`, `DeadEntity`) means the replica's state and the log have diverged. The follower must NOT continue past the failed record, must NOT retry in place (that is what would silently keep a partially applied prefix and diverge), and must NOT invent rollback (that would duplicate the transaction engine). Instead: `Follower` poisons itself — `advance` and `read_at` return a typed `Poisoned` error forever after — and the replica re-joins via state transfer (`recover_world` from a peer, Stage 3 machinery). Poisoning is one `AtomicBool`; the rejoin path already exists.
- **Leader-side corollary**: the same non-atomicity is why INV-3 exists — the leader's only commit path is `Durable` (WAL-first, then apply), so a leader never needs cross-record rollback either; the log is the recovery position.

## 3. Deliverable invariant: the convergence test

The substrate's acceptance criterion is a test, converting the `replicate` example's implicit correctness into a proven invariant:

> 100 mixed transactions (spawn/insert/remove/despawn, heap + POD components) on a leader through `Replicated<S>`; ship batches to a fresh replica world via the transport-agnostic bytes; assert full equality via a **world fingerprint**: order-independent over archetype creation order, hashed by stable `type_name` (never per-world `ComponentId`), entities by `(index, generation)`.

The fingerprint is reusable infrastructure (4.1 uses it for replay-equals-transfer proofs and divergence refusal); it keys identities the way recovery does — by type, never by numeric id.

## 4. Phased plan (Stage 4.0 substrate)

- **4.0-a — Log headers + convergence test.** `view: u64` in WAL frame headers (defaulted for old frames); `tick_after: u64` on each committed WAL record (§2.2 granularity); set-and-verify on replay; world fingerprint; the 100-tx convergence test; follower poison-and-rejoin semantics (§2.7) incl. the poisoning test. View starts at 0 everywhere; `Views` exists minimally (monotonic counter — quorum certificates come with 4.1).
- **4.0-b — Replicated<S> + Follower + read_at.** Component promotion of `replication.rs` primitives; outbound pump behind a `Transport` trait (in-memory channel for tests; TCP later); `read_at` with the `Stale` error.
- **4.0-c — Replica mode.** The World write-mode flag + refusal errors + `apply_batch` documented bypass; failover contract documented on `Changed<T>` docs.
- **4.0-d — (stretch) Follower view fencing.** Views::install stub with durable view record + replay validation against view history (real quorum machinery stays 4.1).

**Sequencing decision recorded**: after 4.0-a lands, Stage 3.75 may proceed **in parallel** — it hooks `read_at` (INV-4) and nothing else. RSM-first insurance is paid by 4.0 alone; 4.1+ (VR core, io_uring, state-transfer wire protocol, client sessions) is decoupled from 3.75.

## 5. Out of scope (deferred, unchanged from roadmap)

VR consensus core (prepare/commit/quorum), leader election, io_uring unified I/O + O_DIRECT + pinned buffers, zero-copy recv-into-WAL buffer identity, generation-isolated slot overwrites with real deposed leaders, client session tables, reducer-intent replication for thin clients, linearizable read leases.

## 6. Testing strategy

- **Convergence test** (§3) — the substrate invariant.
- **Fence test**: append frames at view 0, bump, late view-0 frame → replay drops it.
- **Tick test**: replayed log with tampered record-level `tick_after` → hard error.
- **Replica-mode test**: every public `&mut` entry point on a replica world → typed refusal; `advance` is the only mutation path.
- **Poison test**: a follower fed a record that fails mid-batch (e.g. duplicate spawn) refuses further `advance`/`read_at` with `Poisoned`; state is exactly the applied prefix.
- **Loom**: `applied_seq` advance/read races under the existing loom suite.
- **Fuzz**: `fuzz_wal_replay` extended to view-stamped frames (stale views in the corpus).
- **Deterministic simulation with failpoints**: 4.1 prerequisite, noted here so failpoint hooks are designed (not retrofitted) into the outbound pump and `advance` path.
